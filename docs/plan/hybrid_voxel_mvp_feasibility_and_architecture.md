## 1. 需求背景与核心愿景

本项目（代号 **Celestial**）探索一种**“宏观传统3D场景 + 微观局部体素编辑”**的混合世界架构：
- **宏观世界**：类似《流放者柯南》或魂类游戏的传统 3D 地形与固定场景结构，具备高度精细的美术资产、固定关卡叙事与稳定性能。
- **微观局部体素**：在特定区域（如采矿峡谷、泥泞沼泽、沙地、可挖掘地下矿洞等）动态叠加一层体素网格（Voxel Layer），允许玩家进行深挖、填土、建造庇护所。
- **物理与视觉闭环**：挖掘向下遇到不可摧毁的传统 3D 地形表面时作为“基岩”停止；体素与传统地形之间保持平滑的高度吸附与无缝碰撞。

## 2. 需求可行性深度分析

### 2.1 引擎与语言可行性 (Godot 4.7 Mono + C# / .NET 8)
- **结论**：**可行性极高（Highly Feasible）**
- **性能优势**：Godot 4 的 .NET 8 / C# 运行时为计算密集型操作（如体素三维数组遍历、位运算、顶点缓冲计算）提供了接近 C++ 的执行效率，远超 GDScript。
- **网格与物理 API**：Godot 4 提供了高度灵活的底层网格构建方式：
  - `ArrayMesh` 与 `RenderingServer`：允许直接提交顶点、法线、UV、索引数组，非常适合动态 Chunk 表面网格重建。
  - `ConcavePolygonShape3D` 与 `PhysicsServer3D`：支持根据渲染网格直接更新碰撞几何体，对角色的站立、攀爬、走动提供原生物理支持。

### 2.2 数据模型与内存可行性
- **Chunk 尺寸**：推荐采用 **16×16×16**（4,096 个体素/Chunk）作为标准单元。
  - 采用 1 个字节 (`byte`) 或 2 字节 (`ushort`) 表示 `VoxelType`（材质 ID + 状态标志位）。
  - 单个 Chunk 原始数据仅 4KB ~ 8KB。
  - 一个局部挖掘区域（例如 8×8×4 = 256 个 Chunk）的内存消耗仅在 **1MB ~ 2MB** 级别，内存开销极低。
- **非体素区域轻量化**：对于世界中 90% 以上的非可编辑区域，不实例化任何体素数据结构，仅保留传统 3D 地形网格，确保世界规模不会被体素内存拖垮。

### 2.3 传统地形与体素层的高度对齐与衔接
- **结论**：**技术方案清晰，可行性高**
- **对齐机制**：
  1. 传统 3D 地形表面通过连续函数或高度图纹理 $H(x, z)$ 提供世界高度采样接口。
  2. 当体素区域生成时，体素列底部高度 $y_{min}$ 对齐到 $\lfloor H(x, z) \rfloor$。
  3. **边缘衔接（Skirt / Snapping）**：体素底层方块的底面顶点直接对齐到底层地形的高度采样点，消除接缝与悬空。
  4. **挖掘下限**：体素挖掘操作计算目标体素中心是否低于 $H(x, z)$，低于或等于地形表面时触发“不可挖掘”（视为基岩），停止继续挖空。

### 2.4 物理碰撞与角色交互
- **碰撞统一**：
  - 底层传统地形碰撞体配置为 Collision Layer 1（Environment）。
  - 体素网格碰撞体同样配置为 Collision Layer 1（Environment）。
  - 玩家角色使用标准的 `CharacterBody3D` 结合 `MoveAndSlide()`，无需区分站在传统网格还是体素网格上。
- **边界平滑**：
  - 采用保守的三角形碰撞网格，并设置合理的最大爬坡坡度（`FloorMaxAngle`），确保角色在跨越体素边缘与传统地形交界时不会卡脚。

### 2.5 性能与垃圾回收 (GC) 控制
- **挑战**：网格动态更新如果频繁创建 `float[]` 或 `Vector3[]` 数组，会在 Mono 堆上引起高频 GC 停顿。
- **应对方案**：
  - 使用 `System.Buffers.ArrayPool<Vector3>` 或常驻的顶点生成缓冲区，零临时分配生成网格。
  - 将 Chunk 的网格计算移至后台线程（`Task.Run`），生成完网格数据后再在主线程调用 Godot API 提交至 GPU。

## 4. MVP 目标范围与任务阶段划分

根据 `docs/hybrid_voxel_game_requirements.md`，MVP 重点聚焦于**可玩的核心闭环验证**，剔除复杂的结构坍塌、流体模拟及高级双轮廓面网格。

### 阶段一：基础架构与场景搭建 (Sprint 1)
- [ ] **T1.1 场景与工程脚手架**：Godot 4.7 Mono 项目初始化、C# 解决方案、通用配置与测试场景搭建。
- [ ] **T1.2 传统 3D 地形与采样器**：实现小型固定测试地形（含高度起伏的泥土/岩石凹坑），提供 `IHeightSampler`。
- [ ] **T1.3 体素数据核心结构**：定义 `VoxelType`、`ChunkCoord`、`VoxelChunk`（16×16×16）及内存连续存储结构。

### 阶段二：网格化与分块渲染 (Sprint 2)
- [ ] **T2.1 面剔除网格生成器 (Face-Culling Mesher)**：剔除不可见内部面，生成包含顶点、法线、UV 的 `ArrayMesh`。
- [ ] **T2.2 体素与地形高度贴合 (Height Snapping)**：体素底部与传统地形表面贴合生成，防止断层与漏缝。
- [ ] **T2.3 动态碰撞同步**：生成 `ConcavePolygonShape3D`，实现角色站立与行走。

### 阶段三：玩家交互核心循环 (Sprint 3)
- [ ] **T3.1 第一人称控制器 (Player Controller)**：具备移动、跳跃、镜头旋转与射线拾取（Raycast Pick）。
- [ ] **T3.2 挖掘机制 (Dig Action)**：点击挖掘目标方块，挖到底层传统地形高度时自动阻隔（无法挖掘）。
- [ ] **T3.3 放置机制 (Place Action)**：点击有效表面放置方块，更新相邻体素与邻近 Chunk。
- [ ] **T3.4 边界 Chunk 联动更新**：处于 Chunk 边缘的修改同步刷新邻近 Chunk 网格。

### 阶段四：验证、调试工具与轻量存档 (Sprint 4)
- [ ] **T4.1 调试可视化**：Chunk 边界框（AABB Wireframe）、采样高度线、性能监控器（FPS、网格重建用时）。
- [ ] **T4.2 差异存档机制 (Delta Save)**：仅保存玩家修改过的 Chunk 差异数据，支持存读档验证。
- [ ] **T4.3 体验打磨与边缘渐变**：材质过渡微调与边界碰撞严密性测试。

## 5. 外部工具与生成资产集成 (MCP)

1. **Blender MCP**：
   - 传统 3D 关卡与凹坑地形网格可通过 Blender MCP 程序化或手工雕刻导出为 `.glb` 资产。
   - 传统地形上的岩石、树木装饰模型通过 Blender 生成，导入 `assets/models/`，自动进入 Git LFS 追踪。
2. **Ludo AI MCP**：
   - 快速生成泥土、沙石、草地、矿物等体素纹理贴图草案，导入 `assets/textures/`。
3. **版本控制防膨胀策略**：
   - 所有中间临时工程与烘焙缓存（`.godot/`、`bin/`、`obj/`、`design/**/work/`）全部纳入 `.gitignore`。
   - 模型、贴图与音频必须经由 `.gitattributes` 由 Git LFS 托管。
